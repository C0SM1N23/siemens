\section{Introduction}

\subsection{Purpose of the document}

This document specifies the verification environment applied to the RV32I
processor core, the methodology behind it, and what that environment
establishes about the design.

The verification plan in the annex lists what is checked, and where each
check is applied.

\subsection{Validity of the document}

The document is valid for the verification environment that targets the
processor core described in the Design Specification. Results reported here were
measured on the current revision, on both simulators.

The regression contains further runs that target other blocks. Every figure
reported here is measured over the runs that exercise the core, and excludes
those other runs.

\section{Verification methodology}

\subsection{Overview}

Four mechanisms are used together, because each of them sees something the
others cannot.

\centering

\toprule
\textbf{Mechanism} & \textbf{What it establishes, and what it cannot} \\

Directed self-checking tests &

\subsection{Implementation strategy}

Verification is applied at two levels, and the split is deliberate.

\textbf{System level.} The core executes a real program, assembled from source
into an instruction image, against behavioural memory models. The program is
the checker: it computes results, stores them where the environment can read
them, and drives the sequence of events. This is the closest approximation to
how the core is used, and it is the level at which the interaction between
fetch, execution, the memory interface and the trap mechanism is exercised as a
whole. A second system-level test instantiates two cores against one shared
memory through an arbiter.

\textbf{Block level.} Individual design blocks are driven directly on their own
ports. This level exists for properties a running program cannot isolate:

\begin{itemize}[itemsep=2pt,topsep=3pt]
\item reset values, which a program-driven test has already destroyed by the
      time it observes anything;
\item behaviour at operand boundaries that a hand-written program does not
      naturally produce;
\item each trap cause on its own, so that a single wrong cause is a failing
      test rather than one line among many;
\item structural properties such as full index coverage of the predictor
      arrays, and the boundaries of the return address stack;
\item parameter settings that no core-level run instantiates.
\end{itemize}

\textbf{Bus timing variation.} Every system-level run is repeated under four
memory timing configurations: nominal, high fixed latency, and two seeds of
randomised ready-signal backpressure. A design that only works when every slave
answers immediately has not been verified. The mechanisms that hold state
across a response --- the outstanding-transaction tracking in the fetch stage
and the per-channel handshake tracking in the load/store unit --- are precisely
the ones that fail only when a slave takes its time.

\textbf{Two simulators.} The regression runs on the primary simulator. A second,
independent simulator additionally compiles and runs the assertion layer and the
functional coverage model, which the primary simulator's available edition
cannot. Both flows are run for every revision, so an assertion is live evidence
rather than a description. Compiling the same sources with two front ends is
itself a check, since each tolerates different oversights.

\textbf{Pass criteria.} A run passes only if all of the following hold: every
self-check matched, no protocol monitor recorded a violation, no assertion
fired, and every required functional coverage bin was reached. A missed required
coverage bin fails the run in the same way a mismatched value does, because a
scenario the plan claims and the stimulus never reaches is a hole in the plan,
not a detail.

\subsection{Reference model}

\textbf{No reference model is used.} The environment contains no independent
implementation of the instruction set and performs no instruction-by-instruction
comparison against one.

Expected behaviour is instead determined in one of three ways, depending on the
check:

\begin{itemize}[itemsep=3pt,topsep=3pt]
\item \textbf{Precomputed constants.} For directed tests, the expected value of
      each check is derived by hand from the architecture specification and
      embedded in the test. This is the majority of the checks.
\item \textbf{Self-consistency within the program.} At system level many results
      are chained, so that each value depends on the previous one. A broken
      forwarding path or a lost result therefore propagates into a later value
      rather than cancelling out.
\item \textbf{Protocol rules.} For the bus interfaces the expected behaviour is
      the protocol itself, evaluated continuously rather than compared against a
      recorded trace.
\end{itemize}

The consequence is that instruction-level correctness is
established only for the operand values and instruction sequences the directed
tests actually use. The environment cannot detect an arithmetic error at an
operand value no test applies. This is the main structural limitation of the
current environment, and the reason the arithmetic path additionally receives a
dedicated boundary-value test at block level.

At block level the structure is simpler: the block is instantiated on its own,
a directed driver applies stimulus to its ports, and the same self-checking
comparison mechanism records the verdicts. There are no monitors or coverage
counters at that level; the checks are direct.

\subsection{Control and drivers}

\subsubsection{Clock and reset generation}

A single generator produces the clock and the asynchronous, active-low reset for
every run. Reset release is the starting point of every test, which is what
allows the block-level tests to check reset values before any other activity.

\subsubsection{Instruction supply}

The system-level stimulus is a program written in assembly and translated into
an instruction image loaded by the instruction memory model. The translation
step also emits the address of every label in the program, and the environment
uses those addresses in its checks. This matters for maintainability: a change
to the program that shifts a label updates the corresponding expected value
automatically, instead of silently invalidating a hand-written address constant.

The program is written to exercise every instruction group, every synchronous
trap cause, the CSR access rules and the interrupt sequence, and to leave its
results in architectural registers and in a region of data memory that the
environment reads at the end of the run.

\subsubsection{Bus slave models}

Both bus ports are answered by a behavioural AXI4-Lite slave model with internal
memory. Each model decodes its own address range and answers an access outside
that range with a decode error, which is how access-fault behaviour is
stimulated without an interconnect.

The models carry the timing knobs that make the bus timing sweep possible:

\subsubsection{Interrupt stimulus}

The core's interrupt interface is not driven directly with hand-made request
patterns. Instead the real interrupt controller is instantiated between the
environment and the core, and the environment plays the peripheral sources the
way real peripherals would: a source is raised on an event and held until the
handler clears it. This gives the core realistic request sequencing, including
requests that remain asserted through their own handler.

The source movements are chosen to create specific situations rather than to be
plausible: one source is enabled in the controller but never in the core, so
that it must never be accepted; two sources rise together so that priority order
is observable; and one source rises while a data transaction is in flight, so
that the acceptance boundary is exercised.

At block level, interrupts are applied directly to the core's interface, which
is what allows individual source numbers to be selected deterministically.

\subsection{Monitors and checkers}

\subsubsection{Bus protocol monitors}

One passive monitor instance observes each bus. Monitors drive nothing; they
observe the same signals the design and the slave models exchange and flag a
violation in the cycle it occurs. Checked rules:

\begin{itemize}[itemsep=2pt,topsep=3pt]
\item \textbf{Stability.} Once a valid signal is asserted it remains asserted,
      and its payload remains unchanged, until the handshake completes. Applied
      to all five channels.
\item \textbf{Ordering.} Read data appears only with a read outstanding; a write
      response appears only after both the address and the data handshakes have
      completed; a second request on a channel before the response of the first
      violates the single-outstanding rule.
\item \textbf{Defined values.} No undefined value on a valid or ready signal out
      of reset, and none on a payload while its valid signal is asserted.
\item \textbf{Response legality.} The exclusive-access response encoding is not
      legal on AXI4-Lite and is flagged.
\end{itemize}

Each monitor exposes an error count that must be zero at the end of the run, and
read and write transaction counts. The counts are checked to be non-zero, which
prevents a silent bus from being mistaken for a clean one.

\subsubsection{Assertion layer}

Assertions are bound into the design rather than written into it, so no design
source is modified for verification. Two groups exist.

The assertion layer is compiled and evaluated by the secondary simulator only;
the regression on the primary simulator runs the same tests without it. An
assertion therefore contributes evidence for the system-level run of the
secondary flow and not for the block-level runs, which is why the protocol
monitors duplicate part of the same rule set in ordinary logic: the monitor
checks apply everywhere.

One property in this group was wrong until the trap-active output was exercised
under nesting. It required every return to drop the output, which holds only
when a single trap level is open; a return closing an inner level has to leave
it raised. The behaviour stated above --- a return at the last open level drops
it --- is what the core has always done, and the property now says so, split
into the two cases so that both directions are checked.

\subsubsection{Self-checking comparison}

All directed checks use one comparison mechanism. It compares expected against
observed using a match that treats an undefined value as a mismatch, so a signal
that never resolved cannot pass a check by accident. Each comparison prints a
labelled verdict and increments an error counter on mismatch. A run ends with a
single banner reporting either that all checks passed or how many failed.

This is why the regression is validated by counting banners and verdict lines
rather than by trusting a process exit code.

\subsubsection{Functional coverage}
\label{sec:fcov}

The coverage model counts named scenarios in the cycle they occur, sampled at
four points: instruction commit, trap entry, control transfer resolution, and
bus response handshakes. Counted scenarios include the instruction classes, the
load and store widths, each branch condition in both directions, the four
combinations of prediction against outcome, each trap cause, the CSR operation
forms, the forwarding combinations, the wait-for-interrupt scenarios, the return
stack push and pop cases, the interrupt claims per source, and the bus response
codes including error responses and backpressure.

Each bin is marked required or optional. A required bin that is never reached
fails the run. The optional bins are those that a nominal run legitimately does
not reach: the negative cases that must never occur, and the bins that only the
randomised-backpressure configurations produce.

The coverage report is produced by the secondary simulator flow. On the run
measured for this revision, 88 of 92 bins were reached. The four that were not
are all optional and all of them are bins the nominal configuration cannot
produce: the interrupt source that is deliberately left masked for the whole run
and never claimed, and the two backpressure bins that only the randomised
timing configurations reach. No required bin was missed, so the coverage gate
passed.

\subsection{Simulation environment setup}

\subsubsection{Structure}

The environment is organised in four layers, compiled bottom-up in dependency
order:

\begin{enumerate}[itemsep=2pt,topsep=3pt]
\item the design, ordered from leaf blocks up to the core;
\item the shared verification models --- clock and reset generation, the bus
      slave model, the protocol monitor, and a minimal address decoder and
      arbiter used to build small bus topologies;
\item the system-level tests, which instantiate the core together with those
      models;
\item the block-level tests, each of which instantiates one design block.
\end{enumerate}

Interface wiring for the bus bundles is factored into shared definitions so that
a port list appears once rather than once per test, and the self-checking
comparison is likewise shared.

The compile order is not strictly required by the simulator, which resolves
module instances at elaboration. It is maintained because macro and include
visibility does depend on order, because a missing block is then reported at the
level that needed it, and because downstream tools do require definition before
use.

\subsubsection{Setup and configuration}

Per-run configuration is applied at elaboration through parameter overrides on
the bus models --- read latency, write latency, backpressure rate and seed. Each
configured run echoes the values read back from the elaborated design before it
starts, so the log itself is evidence that the intended configuration was
applied rather than silently ignored.

The prerequisites for running the environment are the two simulators, and a
Python interpreter for the program assembly step. No other tool is required and
no license-managed tool is needed for the assertion flow, which is why the
assertion and coverage layer can also run unattended.
