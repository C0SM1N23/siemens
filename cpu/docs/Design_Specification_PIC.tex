\section{Introduction}

\subsection{Purpose of the document}

This document specifies the design of the programmable interrupt controller:
its architecture, the responsibilities of its functional blocks, the interfaces
it presents to the rest of the system, its software-visible register set, and
the behaviour a system integrator and a driver author must rely on.

\subsection{Validity of the document}

The document is valid for the interrupt controller as currently implemented:
sixteen hardware source lines, sixteen software channels sharing the same
sixteen priority slots, one prioritised request presented to one processor, and
one AXI4-Lite slave port for configuration and status.

Blocks the controller connects to are described only as far as the contract at
the boundary between them and the controller requires.

\section{Specifications and system integration}
\label{sec:integration}

The controller resolves interrupt requests from sixteen sources and presents
one of them at a time to a single processor. It holds no data path, initiates
no bus transaction, and cannot operate standalone. A system integrating it must
supply the following.

\begin{table}[H]
\centering

\addlinespace

\addlinespace

  An AXI4-Lite master with at most one outstanding transaction per direction.
  The slave accepts a second address only after the response to the first has
  been taken. \\
\addlinespace

  Up to sixteen level or pulse signals in the same clock domain, synchronous to
  the controller's clock. The controller attaches no meaning to a particular

  \\
\addlinespace

  A core that samples the offer, replies with a single-cycle claim, and emits a
  single-cycle end of interrupt when a handler returns. The exact timing
  relationship is specified in Section~\ref{sec:cpuiface}. \\
\bottomrule
\end{tabular}
\end{table}

Sources are not the same thing as lines. Each of the sixteen slots can be
raised by its hardware line or by a software write, which gives thirty-two
logical request origins over sixteen priority positions. Once a request is in
the slot the controller does not distinguish the two: they carry the same
priority, the same deadline and the same status bits.

The controller is written in Verilog--2005 within the synthesisable subset, but
the current target is behavioural simulation; see Section~\ref{sec:bugs}.

\paragraph{Constraints the integrator must respect.}
Three properties of the interface are contracts rather than preferences, and
none of them is enforced by hardware.

The claim and the end-of-interrupt pulse must never be asserted in the same
cycle. The depth counter treats the claim as the winning event, so a
coincidence would increment the depth for an interrupt that was simultaneously
supposed to be released, and the accounting would never recover.

The claim must arrive exactly one cycle after the cycle in which the processor
sampled the offer. The controller claims the source number as it stood one
cycle earlier, precisely so that a more urgent source arriving in the meantime
cannot change which source the claim refers to. A master that delays its claim
by an arbitrary number of cycles after sampling will claim the wrong source.

A claim that arrives with no offer outstanding is accepted. It pushes the
source number left over from the last valid offer, and flags that level as
spurious if the source in question is no longer requesting. The accounting stays
consistent either way, so an unprompted claim costs one wasted handler entry
rather than leaving the controller unable to track its levels. The processor is
still expected not to claim unprompted.

\section{Overview of overall structure}
\label{sec:overview}

\subsection{Operating principle}

A request travels through six stages between the source and the handler.

\textbf{Conditioning.} Each slot turns its hardware line into a request
according to its trigger type: a level source requests while its line is high,
an edge source requests from the rising edge of its line until the request is
consumed. The software channel of the same slot is merged in at this point.

\textbf{Enabling.} The merged request is qualified by the per-source enable in
\reg{INT\_ENABLE}. A source that is not enabled produces nothing: it is not
offered, it does not appear in the pending set, and its deadline does not run.

\textbf{Key formation.} Every enabled request is given a ten-bit priority key
built from its band's urgency, its intra-band priority and its slot number. The
key is the only thing the resolver compares, which is what makes the ordering
total and deterministic.

\textbf{Resolution.} A single combinational resolver picks the most urgent
eligible source. Eligibility excludes sources already in service, sources the
processor has masked, and, when something is already in service, every source
that is not strictly more urgent than the interrupt at the top of the nesting
stack.

\textbf{Offer.} The winner is registered and presented to the processor as a
request line plus a source number. Registering it keeps the source lines off
the processor's timing path and gives the pair a stable, consistent value.

\textbf{Accounting.} The claim pushes the source and its key onto the nesting
stack and marks it in service; the end of interrupt pops the stack and releases
it. The snapshotted key, not the current configuration, is what later
preemptions are compared against.

moving a source between bands changes its priority regardless of its intra-band

comparison total: two sources with the same band and the same intra-band

A band number is not compared directly. Each of the four bands is given a
two-bit urgency in \reg{BAND\_CONFIG}, and it is that urgency, not the band
number, that enters the key. Software can therefore reorder the whole priority structure
with one register write, without touching the per-source configuration. Two
bands may be given the same urgency, in which case they merge into one
effective group ordered by intra-band priority and slot number.

\subsection{Data and control flow}

Three flows cross the block and they meet only where the design intends them
to.

\textbf{Configuration} enters through the register port and reaches the
per-source logic directly. A write lands at the end of the cycle in which it
commits, so a source enabled by a write to \reg{INT\_ENABLE} is eligible at the
very next resolution, and a change of band applies from that resolution onwards.
Configuration never passes through the nesting stack, which is why it cannot
disturb an interrupt already in service.

\textbf{Requests} flow from the source lines through conditioning and enabling
into the resolver, and out through the offer register to the processor. The
full set of pending sources leaves the block separately from the offer, because
the processor reports what is waiting, not what was selected: the sources
queued behind the winner have to remain visible to software.

\textbf{Accounting} flows the other way. The claim and end-of-interrupt pulses
move the nesting stack, and the stack feeds back into resolution twice: its
in-service marking removes each serviced source from its own eligibility, and
its top key sets the threshold every candidate must beat.

\section{Interfaces}

\subsection{Hardware interface}

The controller presents four interfaces: clock and reset, the interrupt source
inputs, the processor-facing interrupt interface, and one AXI4-Lite slave port.
All of them are synchronous to the same clock and all outputs are registered
except the AXI4-Lite ready and response-code signals, which the slave front end
drives combinationally from its own state.

\subsubsection{Clock and reset}

One clock edge drives the whole block. Reset is asynchronous and active low,
and every flip-flop in the block is reset, including the nesting-stack arrays
that a valid bit would otherwise cover. The rule applied is that no register
may leave reset holding an undefined value, so that a status read taken in the
first cycle after release returns a defined value and a bus response code can
never be undefined.

Reset is not synchronised inside the block. If the system releases it
asynchronously with respect to the clock, the integrator is responsible for the
release recovery.

The block leaves reset disarmed: \reg{INT\_ENABLE} is zero, so a source line
held high across reset produces no request until software enables it.

\subsubsection{Interrupt source interface}

Sixteen inputs, one per slot, sampled on every clock edge. Their interpretation
is per source and is set by \reg{SRCx\_CONFIG.TRIG}.

A \emph{level} source requests for as long as its line is high. Nothing is
latched, so withdrawing the line withdraws the request, and a source that
disappears before it is claimed simply stops being offered. This is the mode
intended for a peripheral whose own status register holds the condition until
the handler clears it.

An \emph{edge} source is captured on the rising edge of its line into a latch
that holds the request until it is claimed. The line may be a single-cycle
pulse. Two consequences follow from the latch and both matter in practice. A
rising edge that lands in the same cycle as the claim is kept, not swallowed:
the claim consumes the request that is on its way to the handler, and the new
edge stays latched to be serviced afterwards. And an edge captured while the
source is disabled is remembered, so enabling the source presents it
immediately; there is no register that discards a latched edge.

The edge latch is qualified by the trigger type but not by the enable. A slot
left at its reset configuration is level-triggered and captures nothing, so an
unused slot cannot accumulate a stale request; a slot already configured
edge-triggered captures every rising edge whether it is enabled or not.

Unused lines must be tied low all the same, because a level-triggered slot whose
line is high requests the moment software enables it.

\subsubsection{Processor interface}
\label{sec:cpuiface}

Five signals, and the ordering between them is the interface.

The \textbf{enable mask} is an input, not a filter on the output. The processor
supplies the mask it will actually honour, and the controller excludes masked
sources from the resolution itself. Applying it only to the winner would leave
the resolver parked on a source the processor never claims, starving every less
urgent source behind it indefinitely. A masked source stays pending: it appears
in the pending set, its deadline keeps running, and it is offered on the first
resolution after the mask lifts.

The \textbf{request} and \textbf{source number} are registered together from
the same resolution, so the pair is always consistent. The request line is a
level, not a pulse: it stays high while an eligible source is waiting and drops
when the source is claimed or stops being eligible. The source number is only
meaningful while the request is high; when no source is being offered it holds
the last number presented.

The \textbf{pending set} is combinational and reports every source with an
enabled request that is not in service, whether or not the processor's mask
would allow it through. It is deliberately not the same information as the
offer.

The \textbf{claim} pushes the offered source onto the nesting stack. The
controller uses the source number as it stood one cycle before the claim, which
is what makes the claim refer to the source the processor actually saw even if
a more urgent one arrived in the intervening cycle. The \textbf{end of
interrupt} pops the top entry. An end of interrupt received while the stack is
empty is ignored and cannot make the depth underflow.

\paragraph{\reg{NEST\_MAX}, offset \texttt{0xC8}, RW, WARL.}
Bits \texttt{[4:0]} hold the nesting depth limit; the rest read zero. Reset
value 8.

A write is taken only if byte lane 0 is strobed, and the value is taken from
bits \texttt{[4:0]} of the write data without merging the existing contents.
Values outside the range 1 to 16 are clamped: zero becomes one and anything
above 16 becomes 16. Zero is excluded because a limit of zero would mask every
offer permanently, and 16 is the physical stack depth.

While the depth has reached the limit no source is offered, whatever its
priority, and the attempt is recorded in \reg{INT\_STATUS.OVF}. Lowering the
limit below the current depth is permitted and is not destructive: nothing is
unwound, offers are simply withheld until enough handlers have returned.

Bit \texttt{[8]} is set while at least one interrupt is in service; bits
\texttt{[3:0]} give the source at the top of the stack. A handler can read this
register to learn which source it was entered for without consulting the
processor's own cause register, and in a nested situation it names the
innermost level.

same cycle as a clear of the same bit wins, so an event is never lost to a
concurrent acknowledgement.

\subsubsection{Programming sequences}

\paragraph{Bring-up.} Configure before enabling, and enable last.

\begin{enumerate}[itemsep=2pt,topsep=3pt]
\item Write \reg{SRCx\_CONFIG} for every source in use: trigger type, band,
      intra-band priority and deadline.
\item Write \reg{BAND\_CONFIG} if the default order is not wanted, and
      \reg{ESCALATION\_CFG} if any deadline is non-zero.
\item Write \reg{NEST\_MAX} if a limit other than 8 is wanted.
\item Clear \reg{INT\_STATUS} and \reg{SPURIOUS\_LOG} by writing ones.
\item Write \reg{INT\_ENABLE} last.
\end{enumerate}

The order matters for two reasons. A level line that is already high becomes
pending as soon as its enable bit is written, so enabling before the priority is
configured can produce an offer against a half-written configuration. And the
edge detector latches independently of the enable, so any edge that arrived
after the slot was configured edge-triggered is delivered as soon as the source
is enabled. There is no register that discards a latched edge, so a source whose
line may have glitched between its trigger-type write and its enable should have
that first, possibly stale, interrupt absorbed deliberately.

\paragraph{Handler.} A handler entered for a source should:

\begin{enumerate}[itemsep=2pt,topsep=3pt]
\item read \reg{ACTIVE\_VEC} to identify the innermost source, if the processor's
      own cause information is not being used;
\item read \reg{SRCx\_STATUS} and return immediately if \reg{SPUR} is set ---
      the peripheral is no longer asserting and there is nothing to service, but
      the level was accounted and must still be released;
\item clear the condition in the peripheral, which withdraws a level line;
\item return, which produces the end of interrupt that releases the level.
\end{enumerate}

Every claim is accounted, including a spurious one, so every handler entry must
be matched by exactly one return. Omitting the return for a claim believed to be
spurious leaves a level open, and the threshold it sets keeps every source that
is not more urgent from ever being offered again.

\paragraph{Nesting.} Nesting is enabled by the processor re-enabling its global
interrupt enable inside a handler; the controller needs no configuration for it
beyond a \reg{NEST\_MAX} above one. Only a source strictly more urgent than the
innermost level is offered, so a handler that re-enables interrupts cannot be
preempted by an equal or lower priority.

A handler that does this has one obligation of its own, and it belongs to the
processor rather than to the controller. The trap return address and the saved
status each live in a single register, so a second trap overwrites both. A
handler must save them before it re-enables interrupts and restore them
immediately before it returns; without that, the outer handler returns to
wherever the inner one was interrupted rather than to the code it was itself
entered from. The controller's own accounting is unaffected either way --- the
levels still stack and unwind correctly --- which is what makes the omission
easy to miss: it corrupts the program's control flow, not the interrupt state.

\paragraph{Software trigger.} Write the full word \texttt{0xA5A5\_0001} to
\reg{SRCx\_SW\_TRIG}. A narrow write that leaves the key lanes unstrobed is
accepted on the bus and has no effect. The channel clears itself when the slot
is claimed; writing \texttt{0} to bit 0 withdraws it before it is claimed.

\paragraph{Reconfiguring a live source.} A source's band and intra-band
priority may be changed at any time, including while it is in service. The
threshold used for preemption is the key recorded when the source was claimed,
so a change cannot retroactively make an in-service interrupt harder or easier
to preempt; it applies from the source's next wait.

\section{Reuse and reusability}

No component of the controller is sourced from elsewhere. Its AXI4-Lite slave
front end is a separate, reusable element shared with other register-mapped
blocks in the system: it owns the two address channels, the response channels
and the single-outstanding rule, and exposes a committed write and a
combinational read to whatever register file sits behind it. The controller
itself is only that register file plus the resolution logic.

The block has no module parameters. Everything that can be configured is
configured at run time through the register interface, and the two structural
constants are fixed:

\section{Design of submodules}

\subsection{Source conditioning}

\subsubsection{Interface description}

In: the sixteen source lines, the per-source trigger type, the software
channels, the per-source enable, and the claim. Out: one request bit per slot,
consumed by the resolver, by the pending set and by the deadline monitor.

\subsubsection{Functional description}

Each slot forms its request as the trigger-dependent hardware term, merged with
its software channel, gated by the enable. The trigger type selects between the
line itself and the output of an edge latch.

The edge latch is set on a rising edge of the line and cleared when the slot is
claimed. The set has priority over the clear, and that ordering is the design
decision in this block. A rising edge arriving in the same cycle as a claim is
two distinct events: the request being claimed is already on its way to a
handler, and the new one still has to be serviced. Clearing first would discard
it with nothing left to show it ever arrived.

The latch is qualified by the trigger type but not by the enable, so an edge is
captured whether or not the slot is enabled at the time, and is delivered when
software enables it. A slot that has never been configured edge-triggered
captures nothing at all. This is the behaviour described under bring-up in
Section~\ref{sec:regfields}.

The enable is applied at this point, before anything else looks at the request.
A disabled source is invisible everywhere: it is not offered, it does not
appear in the pending set, its \reg{PEND} status bit reads zero, and its
deadline does not run.

\subsection{Priority key formation}

\subsubsection{Interface description}

In: the per-source effective band from the deadline monitor, the per-source
intra-band priority, and \reg{BAND\_CONFIG}. Out: one ten-bit key per
slot.

\subsubsection{Functional description}

The band is translated into an urgency by indexing \reg{BAND\_CONFIG}, and the
key is assembled as shown in Figure~\ref{fig:key}. The translation is what
allows the priority structure to be reordered globally: the resolver never sees
a band number, only an urgency, so a source's rank changes the moment
\reg{BAND\_CONFIG} changes, with no per-source rewrite.

The least significant field is the slot number inverted rather than the slot
number itself, so that a lower slot number produces a larger key. This makes
lower-numbered sources win ties, and more importantly makes ties impossible:
every source has a distinct key in every cycle.

The band that enters the key is the effective band, which is the configured band
except while an escalation is in force.

\subsection{Deadline monitoring and escalation}

\subsubsection{Interface description}

In: the per-source request and in-service state, the per-source deadline, and
\reg{ESCALATION\_CFG}. Out: the effective band, the escalation status bit, the
elapsed-time counter and an escalation event pulse.

\subsubsection{Functional description}

Each slot carries a sixteen-bit counter that runs while the slot is a pending
request awaiting service and a non-zero deadline is configured. It is cleared
whenever either condition stops holding, so it measures the current wait and
not an accumulated one. Being masked by the processor does not stop it: a
source held back by the processor's mask is still waiting, and the whole point
of the deadline is to notice that it has waited too long.

When the counter reaches the configured deadline the source escalates, provided
it has not already escalated during this wait or \reg{MULTI} allows repeats.
Escalation moves the effective band and sets the per-source escalation status
bit together, so the two views cannot disagree. In jump mode the effective band
becomes the configured target. In bump mode it moves one step up the urgency
order.

Bump mode is defined against the urgency order and not against the band
number, and the distinction is not cosmetic. \reg{BAND\_CONFIG} allows the
bands to be reordered, and after a reorder the numerically lower band can be the
less urgent one; a bump that simply decremented the band number would then demote
the source it was supposed to rescue. The implemented rule selects the band with
the lowest urgency that is still strictly above the current one --- the true
next step up --- and holds the band when nothing is more urgent. Under the
default order this reduces to the next lower band number, so the natural
configuration behaves as expected.

Everything resets when the source stops waiting. The effective band returns to
the configured band, the escalation bit clears and the counter clears, which
happens both when the source is claimed and when its request is withdrawn. A
source therefore never carries an escalation from one wait into the next.

\subsection{Priority resolver}

\subsubsection{Interface description}

In: the sixteen requests, the sixteen keys, the in-service marking, the
processor's enable mask, and the top-of-stack key and depth. Out: the winning
source number, its key, and a validity indication.

\subsubsection{Functional description}

The resolver is combinational and evaluates all sixteen slots in the same
cycle. A source is eligible when it is requesting, is not in service, is
allowed through by the processor's mask, and --- when the stack is not empty ---
has a key strictly greater than the key at the top of the stack. Among the
eligible sources the one with the greatest key wins.

Requiring a strictly greater key is what makes preemption well defined. A source
of exactly the same urgency as the interrupt in service is not offered, so a
handler cannot be preempted by its own priority level and two sources cannot
alternate preempting each other.

Comparing against the top of the stack rather than against a running maximum is
what makes nesting unwind correctly: when a level is released the threshold
returns to the level below it automatically, with no separate restore step.

The processor's mask is applied here, inside the eligibility test, for the
reason given in Section~\ref{sec:cpuiface}.

\subsection{Nesting stack and depth limit}

\subsubsection{Interface description}

In: the claim, the end of interrupt, the winning source number and key, and
\reg{NEST\_MAX}. Out: the depth, the top-of-stack source and key, the
in-service marking, and the blocked-preemption event.

\subsubsection{Functional description}

The stack holds one entry per interrupt in service, each entry recording the
source number and the key that source had at the moment it was claimed. A claim
pushes, an end of interrupt pops, and the depth is the number of occupied
entries.

Snapshotting the key rather than recomputing it is the mechanism that keeps
nesting consistent under live reconfiguration. If the threshold were derived
from the current configuration, moving an in-service source into a more urgent
band would raise the bar for everything queued behind it, and moving it into a
less urgent one would allow a preemption that was not permitted when the handler
started. With the snapshot, the threshold a handler runs under is fixed at the
moment it is entered.

The depth limit is enforced by withholding offers, not by rejecting claims. At
the limit the resolver's result is discarded before it reaches the offer
register, so the processor is never shown an interrupt it would not be allowed
to claim, and the situation is recorded in \reg{INT\_STATUS.OVF}. The flag is
informational: nothing is lost, the blocked source stays pending with its
deadline running and is offered as soon as a handler returns.

An end of interrupt received with an empty stack is ignored, so the depth cannot
underflow. A claim received while the depth is already at the limit is ignored
entirely --- no push, no status change, and no consumption of the edge latch or
software channel of the source it names.

\subsection{Spurious claim detection}

\subsubsection{Interface description}

In: the claim, the claimed source number, and the per-source request. Out: the
per-source spurious status bit, the sticky log bit, and the global spurious
event.

\subsubsection{Functional description}

A claim is spurious when the request of the source being claimed is no longer
asserted at the moment the claim lands. This is the case of a level source that
withdrew in the window between the offer being sampled and the claim arriving:
the processor has already committed to entering the handler and cannot take it
back.

A source that is still asserted at the claim and is only cleared later, inside
its handler, is legitimate and is not flagged. The test is applied at the claim
and nowhere else.

The claim is accounted normally even when it is spurious. The level is pushed,
the depth increases, and the handler is expected to return and release it. The
alternative --- refusing the push --- would leave the processor inside a handler
with no matching level to release, and the claim and end-of-interrupt counts
would diverge permanently. Flagging and accounting keeps the two in step and
lets the handler recognise the situation and return early.

Three indications are produced together: a per-source status bit that lives as
long as the level does, a sticky per-source log bit that survives until software
clears it, and a global sticky event flag.

\subsection{Event and status flags}

\subsubsection{Interface description}

In: the escalation pulses, the spurious claim indication and the
blocked-preemption indication. Out: the two sticky registers.

\subsubsection{Functional description}

Both sticky registers apply the same rule: a hardware set in the same cycle as a
software clear of the same bit leaves the bit set. An event that occurs while
software is acknowledging the previous one is therefore never lost, at the cost
of software occasionally seeing a flag it believed it had just cleared.

The global overflow flag is exposed at two addresses over one piece of state,
which means it can only be cleared through \reg{INT\_STATUS}. Reading it from
\reg{NEST\_STATUS} alongside the depth and the top of stack is a convenience for
a handler that is already reading the nesting state.

The per-source spurious log is not cleared by clearing the global spurious
event: the global flag says that something happened, the log says what, and
they are cleared independently.

\subsection{Register interface}

\subsubsection{Interface description}

In: the AXI4-Lite slave port and, from the register file, a combinational
indication of whether an offset is readable and whether it is writable. Out: a
committed write with its address, data and byte strobes, and the read address.

\subsubsection{Functional description}

The write address and write data channels are tracked independently, each with
its own accepted flag, and the write commits when both have been captured. This
allows a master to present them in either order or in the same cycle. A single
commit pulse then carries the address, data and strobes to the register file,
which applies them where the address matches.

Both address channels withhold their ready signal while a response is
outstanding, which enforces the one-transaction-per-direction limit at the
interface rather than relying on the master to respect it.

Whether an access is permitted is decided from the address alone and is
independent of the byte strobes. The write commit pulse is produced for a
rejected write as well, but no register decodes an address outside its own
range, so a rejected write cannot change state.

Reads are registered on the address handshake from a combinational read
multiplexer, giving a one-cycle read latency and a stable value on the data
channel.

Both response-code flags are reset, which matters on the bus and not only in the
reset tree: the response code is driven whether or not the corresponding valid
signal is high, so an unreset flag would present an undefined response code from
time zero until the first transaction completed.

\section{List of bugs and workarounds}
\label{sec:bugs}

No functional defect is currently open against the controller. The entries
below are implementation limitations and deliberate restrictions that a system
integrator or a driver author needs to know about.

\begin{table}[H]
\centering
\caption{Known limitations}
\label{tab:limitations}
\small
\begin{tabular}{@{}L{0.28\linewidth}L{0.60\linewidth}@{}}
\toprule
\textbf{Item} & \textbf{Description and consequence} \\
\midrule
No synthesis result &
  The block is written within the synthesisable subset, but no synthesis or
  timing run has been performed. The resolver compares sixteen keys
  combinationally in one cycle and is the expected frequency limiter; it has not
  been measured. \\
\addlinespace
No module parameters &
  The source count and the physical stack depth are fixed at sixteen. A system
  needing a different source count cannot obtain it by parameterisation. \\
\addlinespace
Address decoding limited to eight bits &
  Only address bits \texttt{[7:2]} are decoded. A decode window wider than 256
  bytes exposes aliases of the entire register file instead of returning an
  error, so the window must be sized to the block. \\
\addlinespace
Protection bits ignored &
  The protection field of both address channels is accepted and discarded.
  Register access cannot be restricted to a privilege or security level. \\
\addlinespace
Claim and end of interrupt not interlocked &
  Asserting both in the same cycle corrupts the nesting accounting
  irrecoverably, and nothing in the block prevents it. This is a constraint on
  the processor, stated in Section~\ref{sec:integration}. \\
\addlinespace
Claim timing is fixed at one cycle &
  The claim must follow the cycle in which the offer was sampled. A master that
  claims later will claim whichever source was being offered one cycle before
  its pulse. \\
\addlinespace
A latched edge cannot be discarded &
  The edge detector latches independently of the enable, and only a claim clears
  it. An edge that arrives between a slot being configured edge-triggered and
  being enabled is therefore delivered once, and software has to absorb it. \\
\addlinespace
Elapsed-time counter stops at the deadline &
  Once a source has escalated as often as the configuration permits, its
  elapsed-time counter holds instead of continuing to count. The field measures
  the wait up to the deadline, not the total wait, and cannot be used to
  measure a long starvation. \\
\addlinespace
Software trigger clear is unguarded &
  Setting a software request requires the key; clearing one does not. A stray
  write of zero to bit 0 of the register withdraws a pending software request.
  \\
\addlinespace
Nesting depth limit register ignores merging &
  A write to the depth limit takes its value from the low five bits of the write
  data and requires byte lane 0; it does not merge with the stored value. A
  narrow write to a higher lane has no effect. \\
\addlinespace
One escalation policy for all sources &
  The mode, the target band and the multiple-escalation setting are global. Only
  the deadline itself is per source, so two sources cannot escalate by
  different rules. \\
\addlinespace
Single processor per instance &
  There is one offer and one claim and end-of-interrupt pair. Distributing
  sources across several processors is not supported. \\
\bottomrule
\end{tabular}
\end{table}

\subsection{Reset state}

Reset is asynchronous and active low, and dominant: it returns the block to the
state below from any state, including one with interrupts in service, without
waiting for a clock edge.
