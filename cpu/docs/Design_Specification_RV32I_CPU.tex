\section{Introduction}

\subsection{Purpose of the document}

This document specifies the design of the RV32I processor core: its
architecture, the responsibilities of its functional blocks, the interfaces it
presents to the rest of the system, its software-visible register set, and the
behaviour a system integrator must rely on.

Where the core is narrower than the instruction set architecture (ISA) it is
based on, the difference is stated at the point where it applies.

\subsection{Validity of the document}

The document is valid for the processor core as currently implemented,
comprising the fetch stage, the combined decode and execute stage, the
writeback stage, and the two bus master interfaces.

Blocks the core connects to are described only as far as the contract at the
boundary between them and the core requires.

\section{Specifications and system integration}

The core is a bus master only. It contains no memory-mapped registers, no
memory and no interconnect, and it therefore cannot operate standalone. A
system integrating it must supply the following.

\begin{table}[H]
\centering
\caption{What the core requires from the system}
\label{tab:integration}
\small
\begin{tabular}{@{}L{0.26\linewidth}L{0.64\linewidth}@{}}
\toprule
\textbf{Resource} & \textbf{Requirement} \\
\midrule
Instruction memory &
  An AXI4-Lite slave reachable on the instruction port, holding executable code
  at the reset vector. The port issues reads only. \\
\addlinespace
Data memory and\newline peripherals &
  AXI4-Lite slaves reachable on the data port. The core issues no transaction
  outside what the running program requests, so the address map is entirely a
  software concern; the core itself decodes no addresses. \\
\addlinespace
Interrupt controller &
  A block that resolves external interrupt sources, presents one prioritised
  request together with its source number, consumes the claim and
  end-of-interrupt pulses the core emits, and reports its full pending set.
  Section~\ref{sec:irqiface} specifies this interface. \\
\addlinespace
Clock and reset &
  One clock. One asynchronous, active-low reset, released synchronously or
  asynchronously; the core contains no clock-domain crossing and no internally
  generated clock or reset. \\
\bottomrule
\end{tabular}
\end{table}

The core implements the RV32I base integer instruction set and the M-mode
subset of the privileged architecture needed for precise traps and external
interrupts. No standard extension is implemented: there is no hardware
multiply or divide, no floating point, no atomic instructions and no
compressed instruction support. Both bus ports comply with AXI4-Lite and use
32-bit addresses and 32-bit data.

The core is written in Verilog--2005 within the synthesisable subset, but the
current target is behavioural simulation; see Section~\ref{sec:bugs}.

\section{Overview of overall structure}
\label{sec:overview}

\subsection{Execution model}

The core executes RV32I in three pipeline stages.

\begin{table}[H]
\centering
\caption{Pipeline stages}
\label{tab:stages}
\small
\begin{tabular}{@{}clL{0.60\linewidth}@{}}
\toprule
\textbf{Stage} & \textbf{Name} & \textbf{Work performed} \\
\midrule
S1 & Fetch &
  Program counter generation, the instruction bus read, and the branch
  prediction lookup for the instruction being offered. \\
S2 & Decode and execute &
  Decode, register read, arithmetic, branch resolution, CSR access, the
  complete data bus transaction, and every exception and interrupt decision. \\
S3 & Writeback &
  Writes the result into the register file. No other effect. \\
\bottomrule
\end{tabular}
\end{table}

Placing decode, execution and the memory access in a single stage means an
instruction either completes in full or produces no architectural effect at
all. That is what makes traps precise without any recovery mechanism: no
half-completed instruction ever exists for a trap to repair. The cost is a long
combinational path through decode, the ALU, address formation and the alignment
check, which would constrain the achievable clock frequency in a synthesised
implementation.

The operand bus drawn as a vertical rail in S2 distributes the two register
operands, after forwarding, to all four execution blocks; the result rail on
the right collects their results into the pipeline register. Only one of the
four produces the value that is finally written back, selected by the writeback
mux according to the instruction class.

The blocks divide into two groups, which matters when judging what a change to
the instruction set would cost. The register file, the arithmetic path, the
load/store unit, the pipeline control and the two bus masters are generic: they
are parameterised by width and by operation code, and nothing in them encodes
which instruction set is being executed. Decode, immediate generation, branch
resolution, exception detection and the CSR file are specific to RV32I and to
the M-mode privileged subset; they are where the instruction encoding, the
cause numbering and the register addresses live.

\subsection{Operating modes}

The core has no mode register and no software-selectable modes. It is always in
M-mode. Its cycle-by-cycle behaviour is one of four conditions.

\begin{table}[H]
\centering
\caption{Operating conditions}
\label{tab:modes}
\small
\begin{tabular}{@{}L{0.20\linewidth}L{0.70\linewidth}@{}}
\toprule
\textbf{Condition} & \textbf{Behaviour} \\
\midrule
Running &
  One instruction completes S2 per cycle. Both bus ports may be active
  simultaneously, each with at most one outstanding transaction. \\
\addlinespace
Stalled &
  S2 holds its instruction. Two conditions cause this: a data transaction in
  flight, and a sleeping wait-for-interrupt instruction. S3 receives bubbles
  for the duration, so nothing commits twice. \\
\addlinespace
Fetch starved &
  S1 has no instruction to offer. S2 is not stalled; it advances with a bubble.
  Throughput is lost, but no state is held. \\
\addlinespace
Sleeping &
  A committed wait-for-interrupt instruction is waiting for a locally enabled
  interrupt to become pending. Instruction fetch is suspended, so the
  instruction bus goes quiet. \\
\bottomrule
\end{tabular}
\end{table}

\subsection{Data flow}

An instruction is fetched by S1 over the instruction bus, together with the
prediction made for it. Both travel to S2 in the pipeline register. In S2 the
instruction is decoded, its operands are read from the register file (bypassed
from S3 where necessary), and exactly one of the execution blocks produces its
result. A load or store instruction additionally runs a complete data bus
transaction inside S2, stalling the stage until the response handshake
completes. At the end of S2 the instruction either commits --- passing its
result to S3, updating the predictor, and updating the CSR file if it is a CSR
instruction --- or is squashed by a trap. S3 writes the committed result into
the register file and has no other effect.

Three events resolved in S2 change the fetch path: a trap, a return from trap,
and a mispredicted control transfer. All three are delivered to S1 as a single
redirect with a target address.

The sections below give the behaviour of each interface and the timing at which
it is exercised.

\subsubsection{Clock and reset}

All sequential logic is triggered on the rising clock edge. The reset is
asynchronously asserted and active low.

Every flip-flop in the core is reset, including the pipeline register payloads
and the predictor arrays, which a valid bit would otherwise cover. The rule
applied is that no register may leave reset holding an undefined value, so that
a two-state and a four-state simulation agree from the first cycle and no bus
output or architectural read can ever return an undefined value. The reset state
of the architecturally visible elements is listed in the annex.

Bus request outputs are held inactive for as long as reset is asserted, as the
bus protocol requires.

\subsubsection{Instruction bus interface}

An AXI4-Lite master port restricted to the read channels. The core never
writes instruction memory, so the write channels do not exist on this port.

\label{sec:irqiface}

global interrupt enable is set, and the enable bit selected by the source

an instruction boundary and never inside a bus transaction, so the preempted
instruction can be re-executed unchanged on return.

Every counter is architecturally 64 bits and is read through a pair of 32-bit

half while the other half still takes that cycle's increment, so a carry is not
lost. Within the written half the CSR operation decides what happens to the
event of that cycle: a plain write replaces the value outright and the event is
discarded, whereas a set or clear operation applies to the already incremented
value and therefore keeps it.

\subsubsection{Programming sequences}

The procedures below follow from the register behaviour above and from the trap
sequencing described in Section~\ref{sec:trapseq}.

\paragraph{Preparing for traps.} Write \reg{mtvec} before enabling anything that
can trap. Until it is written it reads zero, so a trap taken before that point
enters at address zero. In vectored mode the table must have an entry for every
cause that can occur: an external interrupt from source $n$ enters at
BASE~$+$~$4\times(16+n)$, so the sixteen external entries occupy the words at
offset 64 to 124, while every synchronous exception enters at BASE itself.

\paragraph{Enabling an external interrupt.} Three independent enables must all
permit the source, and they are checked in different places:

\begin{enumerate}[itemsep=2pt,topsep=3pt]
\item the enable inside the interrupt controller, which decides whether the
      source is resolved at all;
\item the corresponding bit of \reg{mie}, which the core also exports to the
      controller so that its resolver skips sources this core has masked;
\item \reg{mstatus}.MIE, the global enable.
\end{enumerate}

The order of the three writes does not create a spurious trap in either
direction, because a request that passes only some of them is simply not
accepted. Setting the global enable last is nonetheless the safer habit, since
it is the point after which a handler can actually be entered.

\paragraph{Inside a handler.} On entry the core has already recorded
\reg{mepc}, \reg{mcause} and \reg{mtval}, copied \reg{mstatus}.MIE into MPIE
and cleared MIE. A handler therefore starts with interrupts globally disabled,
and \textbf{must set MIE itself if it wants to be preemptable}. Bit 31 of
\reg{mcause} distinguishes an interrupt from a synchronous exception; for an
interrupt the low bits give $16+n$, for an exception they give the cause code
from Table~\ref{tab:causes}.

\paragraph{Leaving a handler.} Return with the return-from-trap instruction, not
with a jump. The instruction is what restores MIE from MPIE and what closes the
trap level; it is also what emits the end-of-interrupt pulse to the controller
when the level being closed was an interrupt. A handler that returns by jumping
leaves the level open, and the controller will hold that source in service
indefinitely.

\paragraph{Reading a 64-bit counter.} Each counter is read through two 32-bit
addresses and there is no atomic snapshot, so the low half can wrap between the
two reads. The standard sequence applies: read the high half, read the low half,
read the high half again, and repeat if the two high reads differ.

\paragraph{Reading a register without writing it.} A set or clear operation with
a zero source register --- or a zero immediate in the immediate forms --- is
architecturally a pure read and is treated as one here: it does not count as a
write, so it does not raise an exception on a read-only register. This is the
way to sample \reg{mip} or the identification registers. A read/write operation
always counts as a write, even when its destination is the zero register, and
will therefore raise an exception on a read-only register.

\paragraph{Waiting for an interrupt.} The wait instruction suspends execution
until a source enabled in \reg{mie} becomes pending. The global enable is
deliberately not part of the wake condition. The consequence is two different
behaviours: with the global enable set, the wake is taken as a normal interrupt
and \reg{mepc} points at the instruction \emph{after} the wait, so the return
does not re-enter it; with the global enable clear, the wait simply completes as
a no-operation and execution continues in line, with no trap and no handler
entry.

\section{Reuse and reusability}

No component of the core is sourced from elsewhere: every block is written for
this design, so there is no third-party or externally specified element whose
own documentation would have to be consulted.

The core is written as a self-contained, parameterised block with no shared or
global state, and is instantiable more than once in the same system. Its
submodules are individually reusable in the sense that each has a narrow
interface and no hidden dependency on the others, but they are not intended as
standalone deliverables.

software running on separate instances to synchronise through shared memory.

\section{Design of submodules}

\subsection{Instruction fetch}

\subsubsection{Interface description}

Inputs: the redirect request and target from S2, and the prediction produced
for the address currently being offered. Outputs: the instruction bus read
channels, the address to be looked up in the predictor, and the instruction
handed to S2 together with its address, its prediction and a flag marking a
faulted fetch.

\subsubsection{Functional description}

The block owns the program counter and keeps at most one instruction read in
flight. Its behaviour is described by three independent conditions rather than
by a state register: an address request issued but not yet accepted, a read
accepted and its data still owed, and an in-flight read known to be on the
wrong path.

Two mechanisms deserve attention because they are not obvious from the
interface.

\paragraph{Discarding a wrong-path fetch.} An AXI read cannot be withdrawn once
its address has been presented. When S2 redirects the fetch path while a read
is outstanding, the block therefore marks that read for discard, accepts its
data word, drops it, and restarts from the redirect target.

\paragraph{Holding register.} If S2 is stalled when an instruction arrives, the
instruction is parked in a one-entry holding register and no new fetch is
issued until it drains. S1 can therefore never run more than one instruction
ahead of S2. The same mechanism is what silences the instruction bus during
wait-for-interrupt: once the holding register is full, no further address is
issued.

An error response on a fetch does not stall the block. The word is delivered
with a fault marker and traps in S2, which means a fetch error on a wrong-path
instruction is flushed before it can do any harm.

\subsection{Branch predictor}

\subsubsection{Interface description}

A read port used by S1, taking the address being fetched and returning a
predicted direction and target; and a write port used by S2 at instruction
commit, carrying the resolved direction and target plus three hints that
classify the committing instruction as a call, a return, or neither.

\subsubsection{Functional description}

The predictor combines three structures.

\begin{table}[H]
\centering
\caption{Predictor structures}
\label{tab:bp}
\small
\begin{tabular}{@{}L{0.22\linewidth}L{0.66\linewidth}@{}}
\toprule
\textbf{Structure} & \textbf{Function} \\
\midrule
Direction history &
  One bit per entry, holding the last resolved outcome of the control transfer
  at that entry. That bit is the prediction for the next encounter. \\
\addlinespace
Target buffer &
  One 32-bit target per entry. It is what makes prediction possible at all: at
  fetch time the instruction has not been decoded, so a direction bit alone
  cannot say where to jump. \\
\addlinespace
Return address stack &
  A separate stack of return addresses. A return usually has a different target
  from the last time it executed, so the stored target predicts it badly; the
  address to return to, on the other hand, is known exactly at the call. \\
\bottomrule
\end{tabular}
\end{table}

The arrays are direct mapped and indexed by the low address bits, with the
remaining address bits stored as a tag. A lookup predicts taken only on a tag
match with the direction bit set; a miss predicts not taken, which is the only
possible prediction since there is no stored target to jump to. An entry
recorded as a return is predicted from the top of the return stack instead of
from its stored target, falling back to the stored target if the stack is
empty.

The stack is maintained at the same commit point as the other two arrays, so no
predictor state is ever speculative. Calls and returns are identified from the destination and source register
numbers, following the hint encoding defined by the instruction set. An
instruction that links and also returns is treated by that encoding as two
different cases: when the two register numbers are equal it is a call only and
pushes; when they differ it is a return followed by a call, and the stack
replaces its top entry rather than changing its depth.

Stack overflow wraps and discards the oldest entry, and a pop on an empty stack
falls back to the stored target. Both cost prediction accuracy only.
Correctness does not depend on the predictor at any point: the real direction
and target are always computed in S2, and a wrong prediction is corrected by a
redirect.

\subsection{Decode and control}

\subsubsection{Interface description}

Input: the instruction word from the pipeline register. Outputs: the extracted
instruction fields, the immediate value assembled for the instruction format,
and the control signals that steer the rest of S2.

\subsubsection{Functional description}

Field extraction is pure wiring. The immediate generator assembles the
immediate for the five instruction formats from the same instruction bits.

The control decoder is strict: it validates the encoding rather than assuming
it. An unknown opcode, a reserved function field, an undefined load or store
width, an undefined branch condition, or a system instruction that does not
match one of the exact defined encodings all raise an illegal instruction
indication.

An illegal instruction has no architectural effect, but that is guaranteed
downstream rather than by the decoder withholding its outputs. An unknown
opcode leaves every control line at its inactive default; a defined opcode with
a reserved function field still asserts the control lines of its class, and the
illegal indication is raised alongside them. What makes the instruction
harmless in both cases is that the exception it raises squashes it before it
can commit, and that the memory issue is separately conditioned on the
instruction being legal, so no bus transaction is started either.

Two decoding decisions are worth stating:

\begin{itemize}[itemsep=3pt,topsep=3pt]
\item The fence instruction is decoded as a no-operation. The core is a single
      in-order hart with blocking memory accesses, so there is nothing to
      order. The instruction-fence variant is not implemented and is decoded as
      illegal.
\item A CSR instruction produces a register write whose source is the CSR read
      value. The read value is substituted into the arithmetic result path at
      the end of S2, so no separate writeback source is needed.
\end{itemize}

\subsection{Register file and operand forwarding}

\subsubsection{Interface description}

Two combinational read ports addressed from S2, and one write port driven from
S3.

\subsubsection{Functional description}

Thirty-two 32-bit general purpose registers. Register zero is hardwired: it
reads zero on both ports regardless of the array contents, and a write to it is
discarded. All registers are cleared by reset.

The register file write happens on the clock edge that ends S3, so an
instruction in S2 that reads a register the S3 instruction is writing would
otherwise read a stale value. A bypass compares the S3 destination against both
S2 source registers, excluding register zero, and substitutes the writeback
value for the register file output on a match.

This bypass is also what removes the classic load-use penalty. In a three-stage
pipeline a load's data has already reached S3 by the time the consuming
instruction enters S2, so a single backward path covers the case and no stall
cycle is needed.

\label{fig:lsufsm}

The state does not record how far a transaction has progressed, because a write
uses three independent channels --- address, data and response --- and the
address may be accepted before the data or after it. Three per-channel trackers
record which handshakes have completed. The response channel is only made ready
once the channels it depends on have completed: for a read, after the address
handshake; for a write, after both the address and the data handshakes. The
transaction is finished, and the stage released, only when the response
handshake itself completes.

The address, write data and byte strobes are captured when the transaction
starts and driven from that capture thereafter. This is required because the
forwarded operands are only valid in the first cycle --- S3 receives bubbles
while S2 is stalled --- and because AXI requires a stable payload while a
request is waiting to be accepted.

\paragraph{Byte lanes.} A byte or half-word store replicates the data across the
bus and selects the live lanes with the byte strobes; no read-modify-write is
performed. A load shifts the returned word by the address offset and then sign-
or zero-extends according to the instruction, giving the five defined load
forms.

\paragraph{Errors and alignment.} A misaligned access never reaches the bus: it
is detected before issue and trapped. An error response on the bus is reported
to the exception logic, which raises a load or store access fault.

\subsection{Exception detection}

\subsubsection{Interface description}

Inputs: an indication that the instruction in S2 is real and not preempted, the
fetch fault marker, the illegal indications from the decoder and the CSR file,
the environment call and breakpoint indications, the resolved control transfer,
and the state of the data access. Outputs: an exception indication, the cause
code, the associated value, and a signal that blocks the bus issue for a
misaligned access.

\subsubsection{Functional description}

All synchronous exceptions are detected in S2 and resolved by a single priority
chain, so exactly one cause is reported and the cause list exists in one place.
The chain also selects the value recorded alongside the cause.

\begin{table}[H]
\centering
\caption{Synchronous causes, in the order the priority chain evaluates them}
\label{tab:causes}
\small
\begin{tabular}{@{}clL{0.44\linewidth}@{}}
\toprule
\textbf{Order} & \textbf{Cause} & \textbf{Recorded value} \\
\midrule
1 & Instruction access fault (1)        & The instruction address \\
2 & Illegal instruction (2)             & The instruction word \\
3 & Breakpoint (3)                      & The instruction address \\
4 & Environment call from M-mode (11)   & Zero \\
5 & Instruction address misaligned (0)  & The computed target address \\
6 & Load address misaligned (4)         & The effective address \\
7 & Store address misaligned (6)        & The effective address \\
8 & Load access fault (5)               & The effective address \\
9 & Store access fault (7)              & The effective address \\
\bottomrule
\end{tabular}
\end{table}

The numbers in parentheses are the architectural cause codes. The evaluation
order is deliberately not the numeric order: it places the conditions that
invalidate the instruction itself --- a faulted fetch, an illegal encoding ---
ahead of conditions computed from that instruction's operands, so that a
corrupted instruction is never reported as, for example, a misaligned access
derived from its own decoded fields.

Alignment is checked from the effective address before the access is issued, and
only before issue: once a transaction is out, its address was already accepted
as legal, and the arithmetic result feeding the check may change during the
stall.

Interrupts do not pass through this block. They are evaluated at the top level
before execution and suppress the instruction instead.

\subsection{Control and status register file}

\subsubsection{Interface description}

A CSR access port from S2 carrying the address, the write data, the operation
and separate read and write enables, returning the read value and an illegal
access indication. Separate ports for trap entry and return, for the interrupt
enable and pending exchange with the interrupt controller, for the resulting
handler address and return address, and for the counted events.

\subsubsection{Functional description}

The block holds the architectural state listed in Section~\ref{sec:swiface} and
performs the read-modify-write defined for the three CSR operations. Only the
fields that exist are stored; reserved positions are masked before the value
reaches the register rather than being stored and read back, so a later revision
can define one of them without breaking software that happened to write a one
there.

Address checking distinguishes four access classes, and confusing them is the
classic CSR defect, so they are stated explicitly:

\begin{table}[H]
\centering
\caption{Control and status register access classes}
\label{tab:csrclasses}
\small
\begin{tabular}{@{}L{0.18\linewidth}L{0.68\linewidth}@{}}
\toprule
\textbf{Class} & \textbf{Rule} \\
\midrule
Read/write & Reads and writes both take effect. \\
Read-only  & A write raises an illegal instruction exception and the value is
             unchanged. Trapping is required: it is what lets software discover
             the mistake instead of believing the write succeeded. \\
WARL       & A write is accepted without trapping, but only the legal part of
             the value is retained. \\
Tied off   & The register exists but is hardwired to zero. Reads return zero
             and writes are swallowed; neither traps. \\
Absent     & Any access raises an illegal instruction exception. \\
\bottomrule
\end{tabular}
\end{table}

A set or clear operation with a zero source is architecturally a pure read and
does not count as a write, so it does not trap on a read-only register.

Trap entry is atomic with respect to software: it records the return address,
the cause and the associated value, copies the global interrupt enable into its
saved copy, and clears the enable, all on the same clock edge. Trap entry takes
precedence over a software write in the same cycle, so a trapping instruction
never commits its own CSR write. A return from trap restores the enable from its
saved copy and sets the saved copy.

\subsection{Pipeline control}

\subsubsection{Interface description}

Inputs: whether S1 is offering an instruction, whether a data transaction is in
flight, whether a wait-for-interrupt is sleeping, the three redirect requests
from S2, and the register numbers needed for the forwarding comparison.
Outputs: per-stage advance, bubble, squash and redirect commands, and the two
forwarding selects.

\subsubsection{Functional description}

All stall, flush and forwarding decisions are taken in this one block; no stage
manages its own progress. The entire control is a small set of combinational
equations, which means there is no state machine driving the pipeline and
therefore no invalid pipeline state to reach.

\begin{table}[H]
\centering
\caption{Stall and flush sources}
\label{tab:hazards}
\small
\begin{tabular}{@{}L{0.18\linewidth}L{0.68\linewidth}@{}}
\toprule
\textbf{Category} & \textbf{Sources} \\
\midrule
Stall (two) &
  A data transaction in flight, and a sleeping wait-for-interrupt. An
  instruction fetch that is not ready is deliberately \emph{not} a stall: S2
  advances with a bubble instead, which costs the same throughput and removes a
  term from the advance condition. \\
\addlinespace
Flush (three) &
  A mispredicted control transfer, trap entry, and return from trap. All three
  produce the same action --- request a redirect and load a bubble into the
  pipeline register --- so there is one mechanism rather than three. \\
\bottomrule
\end{tabular}
\end{table}

Where a stall and a flush are requested together, the flush wins, because it
invalidates the very instruction the stall was waiting for. The rule has a
second half that comes from the same term: every flush condition is qualified by
the stage advance, so a trap cannot leave S2 while a data transaction is still
outstanding. The bus is therefore never left with a transaction whose response
nobody will accept.

Both pipeline registers carry a valid bit. A cleared valid bit is what makes a
bubble safe: nothing downstream examines the payload, so a flush produces a
guaranteed no-operation whatever the payload holds. The alternative --- injecting
an encoded no-operation --- would require the flush path to drive 32 correct
bits and every downstream decoder to interpret them.

\subsection{Trap sequencing and interrupt handshake}
\label{sec:trapseq}

\subsubsection{Interface description}

Internal to the top level. It consumes the interrupt request and source number,
the exception indication from the exception logic, and the return instruction
indication; it drives the CSR trap ports, the redirect target, and the claim,
end-of-interrupt and trap-active outputs.

\subsubsection{Functional description}

Every architectural decision is taken in S2 in a fixed order:

\begin{center}
interrupt \; $>$ \; synchronous exception \; $>$ \; return from trap \; $>$ \;
mispredicted control transfer
\end{center}

The interrupt is evaluated first, and specifically before the instruction issues
any data transaction, so that a preempted instruction can be re-executed
identically after the handler returns. An exception outranks a misprediction
because a faulting instruction has no correct path left to follow.

The recorded return address differs by trap kind, as the privileged architecture
requires: an exception records the offending instruction, so that a handler that
repairs the fault can retry it, while an interrupt records the instruction to
resume from. A wait-for-interrupt instruction woken by an interrupt is a special
case of the latter: it records the following instruction, so the return does not
re-enter the sleep.

\paragraph{Open trap levels.} The core keeps one bit per currently open trap
level, on a stack sixteen deep, recording whether that level was an interrupt.
Trap entry pushes; a return pops, and emits the end-of-interrupt pulse only if
the popped bit says the level was an interrupt.

\begin{figure}[H]
\centering
\begin{tikzpicture}[x=1mm,y=1mm,>={Stealth[length=2.4mm]},semithick]
  \node[stbi] (run)  at (0,0)   {RUNNING\\\scriptsize depth $=0$};
  \node[stb]  (open) at (98,0)  {TRAP OPEN\\\scriptsize depth $\ge 1$};

\caption{Trap level tracking. The two states describe only whether any trap is

\label{fig:trapstack}

A single in-progress flag would be insufficient, because the same return
instruction closes both kinds of trap and both kinds can be open at once. Two
nested interrupt handlers would send one end-of-interrupt pulse instead of two,
leaving the outer level open in the controller with its source permanently in
service; and a synchronous exception taken inside an interrupt handler would
send an end-of-interrupt on its own return, releasing the interrupt while its
handler was still running. One bit per level removes both cases without any
additional logic: the kind of the trap being closed is the bit popped from the
stack.

The stack is sixteen levels deep, which is also the number of external
interrupt sources the interface can express. Beyond sixteen open levels the
depth counter saturates and the oldest recorded level is shifted out of the
stack, so the end-of-interrupt sequence is no longer guaranteed to be correct.
An interrupt controller must therefore not nest deeper than sixteen levels; the
core does not enforce the limit itself.

\section{List of bugs and workarounds}
\label{sec:bugs}

No functional defect is currently open against the core. The entries below are
implementation limitations and deliberate restrictions that a system integrator
or a software author needs to know about.

\begin{table}[H]
\centering
\caption{Known limitations}
\label{tab:limitations}
\small
\begin{tabular}{@{}L{0.28\linewidth}L{0.60\linewidth}@{}}
\toprule
\textbf{Item} & \textbf{Description and consequence} \\
\midrule
No synthesis result &
  The core is written within the synthesisable subset, but no synthesis or
  timing run has been performed. The long combinational path through S2 noted
  in Section~\ref{sec:overview} is the expected frequency limiter and has not
  been measured. \\
\addlinespace
Instruction fence not implemented &
  The ordinary fence is a no-operation, which is correct for a single in-order
  hart. The instruction-fence variant is decoded as an illegal instruction.
  Software that modifies its own instruction stream is therefore not supported.
  \\
\addlinespace
Counter inhibit absent &
  All counters run at all times and cannot be stopped. The privileged
  architecture permits this; software must not assume it can freeze a counter
  before reading a pair of halves. \\
\addlinespace
Performance counters 8 and above &
  Not provided. They read zero and swallow writes rather than trapping, as the
  architecture requires of counters an implementation does not provide. The
  event selectors are likewise hardwired to zero, so the event assignment in
  Table~\ref{tab:hpm} cannot be changed by software. \\
\addlinespace
No unaligned access support &
  Every misaligned load or store traps. This is architecturally permitted, but
  software or a runtime library must emulate unaligned access if it is needed.
  \\
\addlinespace
Interrupt source count fixed at 16 &
  The source number input is four bits wide and the enable and pending masks
  are sixteen bits, so the interface cannot express more than sixteen external
  sources. \\
\addlinespace
Protection type outputs are constant &
  Both ports drive a fixed protection encoding. A system that uses the
  protection field to distinguish privilege levels cannot do so with this core.
  \\
\addlinespace
Interface deviation from the original requirement &
  An early requirement described the interrupt interface as a per-source
  request vector with a three-bit source identifier. The implemented interface
  is the one specified in Section~\ref{sec:irqiface}: a single prioritised
  request with a four-bit source number, plus an end-of-interrupt pulse that the
  original requirement did not mention. Sixteen sources cannot be identified in
  three bits, and the end-of-interrupt pulse is required for the external
  controller to unwind nested interrupts correctly. This is a difference
  between two requirement sets rather than a defect, and needs a decision before
  the interface is frozen. \\
\bottomrule
\end{tabular}
\end{table}

\subsection{Reset state}

Reset is asynchronous and active low. Every flip-flop in the core is reset,
including the pipeline register payloads and the predictor arrays, which a
valid bit would otherwise cover. The rule applied is that no register may leave
reset holding an undefined value, so that a two-state and a four-state
simulation agree from the first cycle and no bus output or architectural read
can ever return an undefined value.
