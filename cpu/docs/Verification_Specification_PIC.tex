\section{Introduction}

\subsection{Purpose of the document}

This document specifies the verification environment applied to the
programmable interrupt controller, the methodology behind it, and what that
environment establishes about the design.

The verification plan in the annex lists what is checked, and where each
check is applied.

\subsection{Validity of the document}

The document is valid for the interrupt controller as currently implemented and
for the verification environment as it currently exists: five directed
block-level tests, two system-level environments, one passive bus protocol
monitor and one assertion layer.

\section{Verification methodology}

\subsection{Overview}

Three mechanisms are used together, because each of them sees something the
others cannot.

\begin{table}[H]
\centering
\caption{Verification mechanisms and their reach}
\label{tab:mechanisms}
\small
\begin{tabular}{@{}L{0.22\linewidth}L{0.68\linewidth}@{}}
\toprule
\textbf{Mechanism} & \textbf{What it establishes, and what it cannot} \\
\midrule
Directed self-checking tests &
  Establish that a specific scenario produces a specific result. Each test
  carries its own expected values and prints a verdict, so a run is judged by
  counting verdicts rather than by inspecting waveforms. They see only the
  scenarios someone thought to write. \\
\addlinespace
Protocol monitor &
  Establishes that the register port obeys the bus protocol, continuously and
  independently of what the design and the driving master believe is happening.
  It sees protocol violations, not wrong register values. \\
\addlinespace
Assertions &
  Establish invariants that must hold in every cycle of every run in which they
  are active, including cycles no test was written for. They see rule
  violations, not wrong values. \\
\bottomrule
\end{tabular}
\end{table}

There is one further mechanism in the surrounding environment. A functional
coverage model bound into the processor records, among other things, how many
interrupts were claimed and which sources they came from. It observes the
controller only indirectly, at the processor's boundary, and it is evaluated
only by the secondary simulator flow described in Section~\ref{sec:sva}. On the
run measured here every one of its per-source claim bins was reached except the
source deliberately left masked for the whole run.

\subsection{Implementation strategy}

Verification is applied at two levels, and the split is deliberate.

\textbf{Block level.} The controller is instantiated on its own and driven
directly on its source lines, its processor-facing pins and its register port.
This is where the majority of the evidence comes from, for two reasons. Most of
the controller's behaviour is only reachable by a stimulus a processor would
never generate --- a source that withdraws in the one cycle between the offer
and the claim, a rising edge that coincides exactly with a claim, a nesting
limit lowered below the current depth --- and most of it is only observable by
reading registers at a moment a running program could not choose.

Five block-level tests are used, each with a distinct purpose rather than a
distinct feature list.

\begin{table}[H]
\centering
\caption{Block-level tests}
\label{tab:blocktests}
\small
\begin{tabular}{@{}L{0.24\linewidth}L{0.66\linewidth}@{}}
\toprule
\textbf{Test} & \textbf{Purpose} \\
\midrule
Feature test &
  Walks each capability of the controller once along its natural path: a plain
  level interrupt, the three levels of the priority comparison, preemption and
  unwinding, the depth limit, spurious detection, escalation in both modes,
  software triggers, edge sources, and the bus response codes. \\
\addlinespace
Scheduling test &
  The cases where two things happen in the same cycle, or where a programmable
  field is set to something other than its default. These are separated from
  the feature test because a test that only walks the natural path cannot reach
  them. \\
\addlinespace
Reset test &
  The reset contract, checked from the first cycle. A test that spends its
  first hundred cycles configuring the block has already destroyed the evidence
  a reset defect would leave. \\
\addlinespace

  That every register the map calls read-only is read-only, that every bit it
  calls reserved is hardwired to zero, and that the write-one-to-clear and

\addlinespace

  That the hardware puts the right thing into the per-source status register,
  field by field and in both directions. \\
\bottomrule
\end{tabular}
\end{table}

\textbf{System level.} The controller is integrated with a real processor and
real memory models, and the interrupts are produced and consumed by the real
handshake rather than by a driver. This level exists to establish the things the
block level cannot: that a real processor's claim timing satisfies the interface
contract, that the two independent masks interact as intended, and that the
register interface is usable from a program over real bus transactions.

Two environments do this. The processor block's own system test drives the
controller from a program alongside everything else the processor does. The
assembled system adds runs whose subject is the controller itself: a program
that raises each of the sixteen slots in turn, one that has a handler preempted
from inside itself, and one that lets a source miss its deadline and then checks
which handler the processor enters first. Those three reach behaviour a
peripheral-driven run cannot, because the software trigger channels let a
program place a request on any slot at a moment of its choosing, including slots
no device is wired to.

The counted checks are in every case the subset that bears on the controller.

\textbf{Bus timing variation.} The processor system test is repeated under four
memory timing configurations: nominal, high fixed latency, and two seeds of
randomised ready-signal backpressure. The interrupt path is sensitive to this
because the processor defers a claim while a data transaction is in flight, so
the interval between the offer and the claim changes with the memory timing.

\textbf{Pass criteria.} A run passes only if every self-check matched, no
protocol monitor recorded a violation, and no assertion fired in a run where
the assertion layer is active. A test that reaches its end without printing its
own pass banner counts as a failure, and each test prints a distinct banner, so
the regression is judged by counting banners rather than by trusting an exit
code.

\subsection{Reference model}

\textbf{No reference model is used.} The environment contains no independent
implementation of the priority resolution and performs no cycle-by-cycle
comparison against one.

Expected behaviour is instead determined in one of three ways, depending on the
check.

\begin{itemize}[itemsep=3pt,topsep=3pt]
\item \textbf{Precomputed constants.} Reset values, field masks, response codes
      and register contents after a known sequence are derived by hand from the
      specification and embedded in the test. This is the majority of the
      checks.
\item \textbf{The predicted offer.} For a scheduling scenario the expected
      winner is worked out by hand from the priority rules and the test waits
      for exactly that source to be offered, or asserts that a named source is
      never offered over a bounded window. The negative form matters as much as
      the positive one: a resolver that offers everything would satisfy every
      positive check.
\item \textbf{Protocol rules.} For the register port the expected behaviour is
      the protocol itself, evaluated continuously rather than compared against a
      recorded trace.
\end{itemize}

The consequence is that priority resolution is established only
for the configurations the directed tests actually program. The environment
cannot detect a resolver defect that appears at a combination of bands,
intra-band priorities and slot numbers no test constructs; the largest number of
sources contending in any current test is six.

\subsection{Control and drivers}

\subsubsection{Clock and reset generation}

A single generator produces the clock and the asynchronous, active-low reset for
every run. Reset release is the starting point of every test, which is what
allows the reset test to read every register before any other activity has taken
place. The reset test additionally drives reset itself, so that it can apply it
between clock edges from a configured, nested state.

\subsubsection{Source line stimulus}

At block level the source lines are driven directly, and the driver produces
three distinct shapes because three distinct behaviours depend on them: a held
level, a single-cycle pulse for an edge-triggered source, and a transition
deliberately aligned with the same clock edge as a claim. The last of these is
the only way to reach the arbitration between the edge latch being set and the
same latch being consumed.

At system level the environment behaves as a peripheral would. It raises a
source line when the program requests an event and lowers it when the controller
signals that the source has been claimed, which models a device whose status
register is cleared by its handler. Seven of the sixteen lines are driven this
way; one further line is driven by a real block elsewhere in the system, so at
least one source in the run is not under the environment's control at all.

\subsubsection{Processor handshake stimulus}

At block level the claim and end-of-interrupt pulses are driven by the test.
Each is a single-cycle pulse, and the claim is deliberately issued one cycle
after the offer has been observed, so that it lands on the source number the
controller expects to be claimed. This is the same timing relationship the
processor produces, and driving it explicitly is what allows the tests to place
a claim at a moment the processor never would --- immediately after a source has
withdrawn, or while the depth is at its limit.

The processor's own enable mask is held at all ones in every block-level test
except the scheduling test, which is the test that exists to exercise it.

\subsubsection{Register access stimulus}

One shared master task drives the register port in all five block-level tests.
It performs full-word writes, byte-lane writes with an explicit strobe pattern,
and reads, and it checks the response code of every access against the value the
test expects --- so an unexpected error response, or an unexpected success, is a
failure even when the register value happens to be right.

At system level the register accesses are ordinary load and store instructions
executed by the processor, which means the register interface is exercised
through a real bus and a real decoder rather than through a task written for the
purpose.

\subsection{Monitors and checkers}

\subsubsection{Bus protocol monitor}

A passive monitor is attached to the controller's register port in the
system-level environment. It drives nothing and checks four families of rules:

\begin{itemize}[itemsep=2pt,topsep=3pt]
\item \textbf{Stability.} Once a channel asserts its valid signal it must hold
      it, and its payload, until the handshake completes.
\item \textbf{Ordering and outstanding count.} A read response may only appear
      when a read is outstanding, a write response only after both write
      channels have been accepted, and a second request on either direction
      before its response breaks the one-outstanding contract.
\item \textbf{Absence of undefined values.} No valid or ready signal, and no
      payload under an asserted valid signal, may be undefined after reset.
\item \textbf{Response codes.} The exclusive-access response code does not exist
      in this protocol subset and must never appear.
\end{itemize}

The monitor also counts the reads and writes it has seen, and the run checks
that both counts are non-zero. Without that, a port that was never accessed
would pass every protocol rule trivially.

\subsubsection{Assertion layer}
\label{sec:sva}

An assertion layer is bound into the controller without modifying it. It
contains the controller's own invariants and, separately, the same bus protocol
rule set expressed as temporal properties on the register port.

The controller invariants are the ones that must hold in every cycle rather than
at the end of a scenario:

\begin{itemize}[itemsep=2pt,topsep=3pt]
\item the request line and the source number presented to the processor are the
      registered result of one and the same resolution;
\item an offered source is a pending request and is not already in service;
\item an offered source is not one the processor's mask excludes;
\item under nesting, the offered source's key is strictly greater than the key
      at the top of the nesting stack;
\item the depth limit never exceeds the physical stack, and the depth never
      exceeds the limit;
\item the claim and end-of-interrupt pulses never coincide;
\item the depth changes only in response to a claim or an end of interrupt;
\item no offer is presented while the depth is at its limit;
\item an end of interrupt received with an empty stack leaves the depth
      unchanged.
\end{itemize}

The assertion layer is compiled and evaluated only by a secondary simulator,
because the edition of the primary simulator used for the regression does not
support the assertion language. That flow was run for the revision measured
here: the controller's assertions were live in twelve runs and none of them
fired.

The block-level tests run on the primary simulator only, so an assertion covers
the system-level runs and not those. This is why the protocol monitor duplicates
part of the same rule set in ordinary logic: the monitor's checks apply
everywhere.

An assertion is evidence only where the situation it describes actually occurs.
The property that an end of interrupt at depth zero cannot underflow the stack,
for instance, holds in every run without ever being tested, because no run
produces that pulse. The properties credited in the plan are the ones whose
trigger condition occurs in normal operation.

\subsubsection{Self-checking comparison}

Every check compares one observed value against one expected value and prints a
verdict naming the property. A mismatch increments an error count, and a test
ends by printing a pass banner if the count is zero and a failure banner
otherwise. Tests do not stop at the first mismatch, so a single run reports
every property it broke rather than only the first.

Two checking conventions are used in addition to the plain value comparison, and
both exist because the plain comparison is too weak on its own:

\begin{itemize}[itemsep=3pt,topsep=3pt]
\item \textbf{Bounded negative checks.} Several properties are the absence of
      something --- a masked source that must never be offered, an edge that
      must not re-fire, a preemption that must not be allowed. These are checked
      by watching a named source over a bounded window and failing if it appears
      at any point in it, not by sampling once.
\item \textbf{Preconditions that make the check mean something.} A read-only
      register is only proven
      read-only if it held something other than zero at the time of the attempt.
      Every read-only register in the access-class test is therefore first
      driven to a non-zero value by real activity, and the write attempt is
      checked both for the error response and for the register still holding
      what the hardware put there.
\end{itemize}

\subsection{Simulation environment setup}

\subsubsection{Structure}

The environment is built in four layers, compiled in order into one library:
the design; the shared verification models --- clock and reset generation, the
bus models, the passive protocol monitor, the shared register access driver and
the shared comparison mechanism; the tests themselves; and, for the secondary
flow only, the assertion layer and its binding.

Compiling every test into one library in a single pass, rather than per test, is
what makes a name collision or an interface change between the design and a test
a compile error rather than a silently skipped run.

\subsubsection{Scripts}

There are two entry points. The regression compiles once and then executes every
test in turn, each in its own elaboration, printing a banner per run. The
secondary flow compiles the design, the system-level test and the assertion
layer with a different front end and executes the single system-level run with
assertions enabled.

Parameterised runs pass their configuration as an elaboration-time override and
then read the value back out of the elaborated design and print it, so the log
proves the configuration was actually applied rather than silently ignored.

\subsubsection{Setup and configuration}

The block-level tests take no configuration: each drives the controller from
reset and programs it through its own register writes, so a run is reproducible
without external settings. Several of them reset the controller between
independent cases, so that one case cannot inherit state from the previous one.

The system-level runs differ only in the timing of the memory models: read
latency, write latency, and the probability with which a model withholds its
ready signal, with the random sequence seeded explicitly so a failing run can be
repeated exactly.
