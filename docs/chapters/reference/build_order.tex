\chapter{Build and compile order}
\label{ch:buildorder}

This chapter states the order in which the deliverable is compiled, why that
order is fixed, and what to do when a module is added.

\section{Why the order is fixed}

Verilog--2005 resolves module instances at \emph{elaboration}, not at compile
time, so a filelist in arbitrary order normally works --- which is precisely why
the order is worth pinning down rather than leaving to chance. Four things do
depend on it. Macro and \verb|`include| visibility is order-dependent within a
compilation unit. A duplicate module or a clashing parameter name is reported
against whichever copy the compiler saw first. A module missing from the list is
reported at the level that needed it under a bottom-up order, and as one
unresolved instance at the top of the hierarchy under any other. And lint,
synthesis and formal front-ends do require definition before use, so the same
list can be handed to them unchanged.

\begin{rtlnote}
The rule is enforced in one place. \file{debug/sim/rtl.f} is the single source of
truth for the RTL source set \emph{and} its order, and both flows read it ---
\texttt{vlog -f rtl.f} and \texttt{verilator -f rtl.f}. A module is added to the
project in exactly one location. Each module also includes \file{defines.vh}
itself, under an include guard, so no file depends on a macro another file
happened to define earlier.
\end{rtlnote}

Two orderings inside that table are load-bearing rather than cosmetic. The
arbiter must precede the dual-core bench that instantiates it, for the same
legibility reason as the RTL. The \sig{bind} file must be compiled
\emph{last} of all, because a bind statement names both the target module and
the checker module and needs both to exist.

\section{Adding a module}

\begin{enumerate}[leftmargin=*,itemsep=2pt]
\item Place it at the lowest level that is still strictly above everything it
instantiates.
\item Insert it alphabetically within that level in \file{rtl.f}, with the
one-line comment naming what it instantiates.
\item If it introduces a new level, add the level header rather than widening
an existing one.
\end{enumerate}

Nothing else changes: \file{compile.do}, \file{regress.do} and
\file{run\_verilator.sh} all read the filelists, so neither flow is edited.

A clean compile is part of the pass criterion, not a courtesy: every source file
carries its own \verb|`timescale| so the result never depends on filelist order,
and every comparison, index and assignment is width-explicit rather than relying
on implicit extension or truncation.
